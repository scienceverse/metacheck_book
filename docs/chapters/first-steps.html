3  Your First Check

This chapter does not explain anything about how Metacheck works. It just walks through the four things you will do most often, using two short example papers, so that you have something working before you read about how any of it works. If you have never used R before, that is fine: every line below is explained, and you can copy and paste each code chunk into the R console one at a time.

We will use two small manuscripts, both about the same simple study (whether people are slower to name the ink color of a word when the word itself names a different color — the “Stroop effect”):

  • A good paper: https://github.com/Lakens/stroop_effect_paper, which reports its statistics correctly and shares its data and code openly.
  • A bad paper: https://github.com/Lakens/stroop_effect_paper_bad, a version of the same study with a number of common mistakes deliberately introduced, so you can see what Metacheck flags when something is wrong.

3.1 Step 1: Read in a paper

Metacheck works with PDF files. The function convert() turns a PDF into a structured format Metacheck can read, and read() loads that structured format into R as a paper object — everything Metacheck does, in every later chapter, starts from a paper object like this one.

Since our example papers live on GitHub, we first download the PDF with download.file(), a base R function that needs no extra packages:

download.file(
  "https://raw.githubusercontent.com/Lakens/stroop_effect_paper/main/output/analysis.pdf",
  destfile = "good_paper.pdf", mode = "wb"
)

Now convert the PDF and read it in:

json_file <- convert(file_path = "good_paper.pdf", save_path = ".")
paper <- read(json_file)

convert() sends the PDF to a free conversion server and gets back a structured file; this needs an internet connection and takes a few seconds. You only need to do this once per paper — after that, you can read() the saved file directly, without converting again.

Note

convert() defaults to a server at Eindhoven University of Technology that does not store your manuscript. See Reading in a Paper if you would rather run your own, fully local conversion server.

3.2 Step 2: Run one check

Metacheck organises its checks into modules. Each module looks for one specific thing. module_run() runs a single module on a paper object. Just printing the result shows a short report:

module_run(paper, "stat_effect_size")

Effect Sizes in t-tests and F-tests: All detected t-tests and F-tests had an effect size reported in the same sentence.

stat_effect_size checks whether a reported statistical test (like a t-test) is accompanied by an effect size, and whether that effect size is actually consistent with the test. Every module gives a traffic light — green (no issues found), yellow (worth a closer look), red (a likely problem), or “na” (nothing for this module to check) — plus a short summary. The good paper reports t(130) = 18.04 together with Cohen’s dz = 1.58, and that effect size is indeed what you would expect from a test statistic that size — hence the green light above.

Now download the bad paper’s PDF the same way as in Step 1, and run the same check on it:

download.file(
  "https://raw.githubusercontent.com/Lakens/stroop_effect_paper_bad/main/analysis.pdf",
  destfile = "bad_paper.pdf", mode = "wb"
)
json_file <- convert(file_path = "bad_paper.pdf", save_path = ".")
bad_paper <- read(json_file)
module_run(bad_paper, "stat_effect_size")

Effect Sizes in t-tests and F-tests: All effect sizes were reported, but some appear inconsistent with the test statistic. This can be because the effect size is not clearly labeled (e.g., d, instead of d_rm), because the effect sizes is not reported with enough precisions (e.g., 0.3 instead of 0.32), or because the effect size is incorrectly reported.

This comes back red: it reports the same t-test, t(130) = 18.04, but with a Cohen’s dz of 0.25 — a value nowhere near what that test statistic implies. Metacheck does not know which number was typed wrong, but it correctly flags that the two do not agree, which is exactly the kind of inconsistency a reader re-typing numbers by hand is likely to miss.

3.2.1 Getting specific pieces of information out

Printing the result is useful for reading, but if you want to use a piece of it elsewhere — say, to check many papers automatically — assign the result to a variable first, and then pull out just the part you need with $:

mo_bad <- module_run(bad_paper, "stat_effect_size")
mo_bad$traffic_light
#> [1] "red"
mo_bad$summary_text
#> [1] "All effect sizes were reported, but some appear inconsistent with the test statistic. This can be because the effect size is not clearly labeled (e.g., d, instead of d_rm), because the effect sizes is not reported with enough precisions (e.g., 0.3 instead of 0.32), or because the effect size is incorrectly reported."

mo_bad$traffic_light gives you just the colour, and mo_bad$summary_text gives you just the plain-language summary — the same two pieces of text that were part of the printed report above. Every module’s result has more than this; see Running the module in the Modules part of this book for what else is in there.

You now know the single most important function in Metacheck: module_run(paper, "module_name"). Every module in the Modules part of this book works exactly this way — only the module name changes.

3.3 Step 3: Create a full report

Most of the time you will not want to run modules one at a time — you want every relevant check, in one document. report() runs a whole battery of modules and writes the result to an HTML file you can open in a browser:

report(paper, output_file = "good_paper_report.html")

This writes good_paper_report.html into your working directory. Open it, and you will see the same traffic lights and summaries from Step 2, but now for every module the report includes — preregistration, funding, conflicts of interest, power, statistical reporting, and more — all in one place, ready to read or share.

Running report() on the bad paper’s PDF (downloaded the same way as in Step 1, from https://github.com/Lakens/stroop_effect_paper_bad/blob/main/analysis.pdf) produces the same kind of report, but with several more red and yellow lights: a missing ethics statement, a missing funding statement, an unwarranted causal claim, p-values that do not match their own reported statistics, and more. Nothing about the process changes between the two papers — only what the report finds.

3.4 Step 4: Check a shared repository

So far we have checked what a paper says. Metacheck can also check what a paper’s authors actually shared — the data and code repository itself — independently of any manuscript. repo_check is the module for this, and it works on a local folder, so you do not need a paper object at all.

Download the bad paper’s repository as a zip file (the same “Download ZIP” button you would click on GitHub) and unpack it:

download.file(
  "https://github.com/Lakens/stroop_effect_paper_bad/archive/refs/heads/main.zip",
  destfile = "bad_repo.zip", mode = "wb"
)
unzip("bad_repo.zip", exdir = "bad_repo")

Then point module_run() at the unpacked folder. Because there is no manuscript to search for repository links, two extra arguments tell Metacheck to look at this folder directly instead: local_path says where, and local_only = TRUE says not to look anywhere else.

mo <- module_run(test_paper(), "repo_check",
                 local_path = "bad_repo/stroop_effect_paper_bad-main",
                 local_only = TRUE)
mo$traffic_light
mo$summary_text

test_paper() creates an empty, placeholder paper object — repo_check needs a paper object to attach its results to, but since we are not reading any manuscript in this step, an empty one is all that is required.

This reports a yellow light on the bad repository: among other things, Metacheck cannot confidently classify every file it finds, and flags a file naming problem. Try the same two lines on the good paper’s repository (https://github.com/Lakens/stroop_effect_paper) and compare the result — it is organised into clearly labelled data/, code/, output/, and documentation/ folders, with a complete codebook, which is exactly what repo_check is designed to reward.

3.5 What you have just done

In four short steps, you:

  1. Read a PDF into R as a paper object (convert() + read()).
  2. Ran a single check on it (module_run()).
  3. Generated a full, shareable report (report()).
  4. Checked a shared repository on its own, with no manuscript involved (module_run() with local_path/local_only).

These four functions cover the large majority of what you will do with Metacheck day to day. Everything else in this book is about the details: which modules exist and what each one checks (Modules), how reading in a paper actually works (Reading in a Paper), how to search a paper’s text yourself (Text Search), and how to turn on a large language model for the modules that can use one (Using Large Language Models).
